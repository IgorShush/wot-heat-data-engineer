# Problem 2 - Graphics Settings Schema Design

## Overview

The goal is to store the graphics settings a player used for every battle, based on the settings menu shown in the game client. The design must be effective at **billions of rows** of battle data.

The settings menu contains **16 individual settings** across four groups:

| Group | Setting | UI Type | Data Type |
|---|---|---|---|
| Display | Resolution | Dropdown | VARCHAR |
| Display | Display Mode | Dropdown | VARCHAR |
| Display | Monitor | Dropdown | VARCHAR |
| Field of View | Ability Camera | Slider (degrees) | SMALLINT |
| Field of View | Sniper Camera | Slider (degrees) | SMALLINT |
| Field of View | Third-Person Camera | Slider (degrees) | SMALLINT |
| Dynamic Camera Effects | Linear Impact Effect | Slider (%) | SMALLINT |
| Dynamic Camera Effects | Angular Impact Effect | Slider (%) | SMALLINT |
| Dynamic Camera Effects | Tilt Effect | Slider (%) | SMALLINT |
| Dynamic Camera Effects | V-Sync | Checkbox | BOOLEAN |
| Dynamic Camera Effects | Gamma | Slider (decimal) | NUMERIC(4,1) |
| Graphics Settings | Quality Preset | Dropdown | FK → lookup |
| Graphics Settings | General | Dropdown | FK → lookup |
| Graphics Settings | Objects | Dropdown | FK → lookup |
| Graphics Settings | Terrain | Dropdown | FK → lookup |
| Graphics Settings | Lighting | Dropdown | FK → lookup |
| Graphics Settings | Shadows | Dropdown | FK → lookup |

---

## The Core Problem: Repeated Data

The naive approach - one wide row per battle participant with all 16 settings as columns - works but is extremely wasteful at scale.

**Why?** Most players almost never change their graphics settings. A player might play 2,000 battles with the exact same configuration. The naive approach stores all 16 values 2,000 times, identically.

---

## Solution: Settings Snapshot + Deduplication

Instead of storing the full settings on every battle row, we store each **unique combination of settings exactly once** in a `graphics_profiles` table. Each battle just stores a reference to the matching profile.

```
graphics_quality_levels  (lookup: MINIMUM / LOW / MEDIUM / HIGH / ULTRA)
         │
         ▼
graphics_profiles        (one row per UNIQUE settings combination)
         │
         ▼
battle_graphics_settings (one row per participant per battle - just two columns)
         │
         ▼
battle_participants       (from Problem 1)
```

---

## Tables

### `graphics_quality_levels`

Lookup table for the shared dropdown values used across all six graphics quality settings.

| Column | Type | Notes |
|---|---|---|
| `level_id` | SERIAL PK | |
| `name` | VARCHAR(32) | e.g. `MINIMUM`, `LOW`, `MEDIUM`, `HIGH`, `ULTRA` |

> All six graphics dropdowns (Quality Preset, General, Objects, Terrain, Lighting, Shadows) share the same set of valid values, so one lookup table serves all of them. This avoids six separate lookup tables with identical content.

---

### `graphics_profiles`

Stores each unique combination of all 16 settings exactly once.

| Column | Type | Notes |
|---|---|---|
| `profile_id` | BIGSERIAL PK | Surrogate key |
| `settings_hash` | CHAR(32) UNIQUE | MD5 of all setting values - used for deduplication |
| `resolution` | VARCHAR(16) | e.g. `1920x1080` - hardware-dependent, stored as string |
| `display_mode` | VARCHAR(32) | e.g. `WINDOWED`, `FULLSCREEN`, `BORDERLESS` |
| `monitor` | VARCHAR(128) | Monitor model name as reported by the OS |
| `fov_ability_camera` | SMALLINT | Degrees, 1–360 |
| `fov_sniper_camera` | SMALLINT | Degrees, 1–360 |
| `fov_third_person_camera` | SMALLINT | Degrees, 1–360 |
| `dce_linear_impact_effect` | SMALLINT | Percentage, 0–100 |
| `dce_angular_impact_effect` | SMALLINT | Percentage, 0–100 |
| `dce_tilt_effect` | SMALLINT | Percentage, 0–100 |
| `dce_vsync` | BOOLEAN | Toggle |
| `dce_gamma` | NUMERIC(4,1) | Decimal, e.g. `2.2` |
| `gfx_quality_preset` | INT FK | → `graphics_quality_levels` |
| `gfx_general` | INT FK | → `graphics_quality_levels` |
| `gfx_objects` | INT FK | → `graphics_quality_levels` |
| `gfx_terrain` | INT FK | → `graphics_quality_levels` |
| `gfx_lighting` | INT FK | → `graphics_quality_levels` |
| `gfx_shadows` | INT FK | → `graphics_quality_levels` |

**Why `settings_hash`?**
Before inserting a new profile, the application computes an MD5 digest of all 16 setting values concatenated together. It then checks whether a row with that hash already exists using `ON CONFLICT (settings_hash) DO NOTHING`. If the profile already exists, it just reads the existing `profile_id` and reuses it. This is the deduplication mechanism.

**Why `BIGSERIAL` and not UUID for `profile_id`?**
Unlike battles, profiles are not generated by distributed game servers - they are created centrally when the first battle using that configuration is recorded. A sequential integer is cheaper to store and faster to join on, especially since `profile_id` appears as a FK in every row of `battle_graphics_settings`.

---

### `battle_graphics_settings`

Links a battle participant to their graphics profile. This is intentionally minimal.

| Column | Type | Notes |
|---|---|---|
| `participant_id` | UUID PK/FK | References `battle_participants` |
| `profile_id` | BIGINT FK | References `graphics_profiles` |

This table grows at the same rate as `battle_participants` - one row per player per battle. But each row is only ~24 bytes (UUID + BIGINT), making it extremely compact even at billions of rows.

---

## Write Flow

```
1. Player finishes a battle with a known settings configuration.

2. Application computes:
   hash = md5(resolution || display_mode || monitor || fov_ability || ...)

3. Upsert into graphics_profiles:
   INSERT INTO graphics_profiles (settings_hash, resolution, ...)
   VALUES (hash, '1920x1080', ...)
   ON CONFLICT (settings_hash) DO NOTHING;

4. Look up the profile_id:
   SELECT profile_id FROM graphics_profiles WHERE settings_hash = hash;

5. Insert the link:
   INSERT INTO battle_graphics_settings (participant_id, profile_id)
   VALUES (participant_uuid, resolved_profile_id);
```

---

## Storage Comparison

Consider a player who plays **2,000 battles** without changing settings.

| Approach | Rows stored | Approximate size per row | Total |
|---|---|---|---|
| Naive (wide table) | 2,000 | ~120 bytes | ~240 KB |
| Snapshot + deduplication | 1 profile + 2,000 links | ~120 bytes + ~24 bytes | ~120 bytes + ~48 KB |

At millions of players, the savings compound significantly. Most importantly, analytical queries like *"how many players play on MINIMUM graphics?"* only need to scan `graphics_profiles` (a tiny table) rather than billions of participant rows.

---

## Answering the Task Requirement

> "Suggest the most effective way to store the data."

The snapshot + deduplication pattern is the most effective because:

1. **Space efficiency** - each unique settings combination is stored once, regardless of how many battles reference it.
2. **Write efficiency** - `ON CONFLICT DO NOTHING` makes deduplication a single atomic operation with no application-level locking.
3. **Query efficiency** - analytics on settings distributions scan `graphics_profiles` (thousands of rows), not `battle_graphics_settings` (billions of rows).
4. **Extensibility** - adding a new setting means one new column in `graphics_profiles` only, with no impact on the link table or battle data.
